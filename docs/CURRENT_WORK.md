- **Learning time zone:** default System, meaning `TimeZoneInfo.Local` (OS timezone) only — no GPS, IP geolocation, location permission, account, cloud, or network dependency. Explicit selection uses a bounded, curated catalog (`KnownFirst.Core.Settings.LearningTimezoneCatalog`) of 50 canonical IANA timezone identifiers (spanning inhabited UTC-11 through UTC+14, including `Pacific/Pago_Pago`, `Pacific/Chatham`, `Pacific/Tongatapu`, and `Pacific/Kiritimati`); the catalog stores only the canonical ID, never a UTC offset. Settings option labels have the user-facing form `(UTC±HH:mm) City`, with the offset computed at render time from `TimeZoneInfo`/`DateTime.UtcNow` (dynamic, DST-aware, including Chatham UTC+12:45 standard / UTC+13:45 daylight) rather than persisted. An invalid persisted timezone ID still fails safely to System behavior through the existing, unmodified `LearningTimezoneResolver`. EN/DE/RU localization is complete (50/50 catalog city names in each language). **Evidence boundary:** Windows/.NET runtime resolution of all 50 catalog IDs was verified (via `Catalog_EveryCuratedIdResolvesOnTheCurrentPlatform` and `Catalog_CoversInhabitedEdgeTimezones`). Android runtime resolution, emulator/device validation, and Android timezone-runtime proof were **not** performed and remain unverified; the later mandatory `FULL_VALIDATION` Android Debug/Release **build** gates are not equivalent to Android runtime/device proof.
- **New learning day begins at:** default 00:00; deterministic two-part 24-hour selector (`#learning-day-cutoff-hour` covering `00`..`23`, `#learning-day-cutoff-minute` covering `00`..`59`, separated by visual colon `.time-separator`) with localized accessible labels (`Settings_LearningDayCutoffHours`, `Settings_LearningDayCutoffMinutes`), replacing native `<input type="time">` without AM/PM or host regional format dependencies; the valid stored domain remains 0..1439 minutes, unchanged in `LearningDayConfiguration.NormalizeCutoffMinutes`; arbitrary values such as 07:37 are valid; `24:00` is impossible. The value is interpreted using the existing `LearningDayConfiguration`/`LearningDayBoundaryPolicy` and the selected learning timezone; no duplicate cutoff policy exists. Existing Schema-12 `ActiveBudgetDay`/Bridge/rollover semantics are unchanged — `Services/Study/LearningService.cs`, `LearningDayBoundaryPolicy`, and `Data/` show no diff in this candidate.
- **Restore default settings vs. Reset all application data:** these are two distinct contracts, deliberately kept separate.
  - **Restore default settings** is non-destructive: it restores the target defaults above (settings, theme preference, language preference) and **preserves the user's current online-dictionary lookup consent exactly as it is** — granted stays granted, not granted stays not granted. It does not call `Database.ResetAsync()`, does not call `Preferences.Clear()`, and does not touch vocabulary, learning cards, review/learning history, imported documents, other database content, Display Name, onboarding state, What's-New/version state, or any other unrelated persisted product state.
  - **Reset all application data** remains the separate destructive action, remains last in the Settings product order, and retains its existing destructive confirmation, `Database.ResetAsync()` call, and `Preferences.Clear()` call. After a full reset, online-dictionary lookup consent is always false/not granted (unconditionally revoked, independent of whatever the in-memory consent value was immediately before `Preferences.Clear()`), and ordinary settings defaults are restored afterward via the same shared default-restoration policy (`Services.Settings.SettingsDefaultsService`, exposing `RestoreDefaults()` for the non-destructive path and `RestoreDefaultsForFullReset()` for the destructive path, so both flows cannot drift apart on the target defaults while keeping the consent contracts distinct).
